# Глобальные правила работы

## Порядок работы

1. Сделал фичу или фикс → `/test <файл>`, если в проекте есть тестовый фреймворк.
2. `/review` → **только** перед коммитом рискованных изменений: несколько файлов, безопасность, деньги, данные, рефакторинг, новый код. Мелкая правка, текст, одна кнопка, конфиг — коммить без ревью. Авто-коммит из п. 5 ревью не требует.
3. README и docs обновляй **сам** и только если изменились запуск, установка, API, CLI, env или структура. Сабагента `docs` зови только по прямой команде `/docs` — не после каждой задачи.
4. Одна строка, опечатка, форматирование → ничего не запускай, делай сам.
5. Закончил задачу, где менялись файлы, и проект — git-репозиторий с remote `origin` → **сам** сделай `git add -A`, commit, `git pull --rebase`, `git push`. Не жди слова «сохрани». Если remote нет — ничего не делай.
6. Модель по умолчанию — дешёвая (`deepseek-v4.1-flash-1017`). Если задача явно тяжёлая (архитектура, рефакторинг многих файлов, неочевидный баг) — скажи одной строкой: «для этого лучше `/pro`». Сам модель не меняй.

## Что делает каждый сабагент

- `reviewer` (`/review`) — только читает `git diff`/`git status`, ищет баги. Ничего не меняет.
- `tester` (`/test файл`) — пишет тесты, запускает их, чинит только тесты. Прод-код не трогает.
- `docs` (`/docs`) — обновляет README и docs. Код не трогает.

## Главное правило (запомнить навсегда)

**Ничего не ломать из того, что уже сделано.** Рабочий функционал, готовые разделы,
кнопки, окна, настройки не удаляются и не «переносятся» по своей инициативе.
Убирать или переделывать можно **только** то, на что пользователь указал конкретно
(«убери вот это», «перенеси вот эту кнопку»). Задача «добавь / поправь X» — значит
трогаем X и ничего больше. Сомневаешься — не трогай существующее, добавь рядом.

## Ограничения

- Не запускай сабагентов для одной строки, опечатки или форматирования.
- `tester` не устанавливает зависимости. Если тест-фреймворка нет — он сообщает и останавливается.
- `reviewer` не работает вне git-репозитория — он сообщает и останавливается.
- Если сабагент упал (лимит, ошибка) — не запускай его второй раз. Сделай работу сам и скажи, что сабагент не смог.
- Не запускай несколько сабагентов подряд без необходимости: это тратит токены и время.
- **Не читай картинки** (`png`, `jpg`, `jpeg`, `webp`, `gif`) инструментом `read`. Модель по умолчанию не поддерживает изображения, и сессия падает с ошибкой 400. Чтобы показать картинку пользователю — `browser.preview`. Если нужно именно проанализировать изображение — скажи, что нужна vision-модель.

## Команды

- `/review [цель]` — ревью текущих изменений, только чтение.
- `/test <файл>` — тесты для файла или модуля.
- `/docs [цель]` — README и документация.
- `/sync` — commit, pull --rebase и push в GitHub.

## Синхронизация с GitHub

Синхронизация запускается **сама** в конце задачи с изменениями (п. 5). Дополнительно — по словам «сохрани», «синхронизируй», «залей на GitHub», «сделай бэкап проекта»:

1. Проверь, что это git-репозиторий и есть remote `origin`. Если нет — сообщи и остановись.
2. `git add -A`; если есть изменения — `git commit -m "..."` с коротким описанием.
3. `git pull --rebase origin <ветка>`, затем `git push origin <ветка>`.
4. Не делай `git push --force`, `git reset --hard`, не коммить секреты.
5. Покажи, что именно ушло: ветка, коммит, файлы.

В проектах `sketch_CG` и `AirfoilStudio` есть готовый `tools\sync-now.cmd` — можно запускать его без OpenCode.

## Документация

- В каждом проекте, который живёт больше недели, должен быть README.md: что это, установка, запуск, env, пример, тесты.
- README пиши кратко и по делу, на русском, если проект не международный.
- Не выдумывай команды: проверяй их по package.json, pyproject.toml, Makefile или CI.
